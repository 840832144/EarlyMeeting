# 发卡日志与日期校验

2026-09-21，TASK-0028，PR #4。Subagents: none。

## 已定位的问题

云端日志显示9月21日09:30两个群各发送一次；随后系统日期跳到12月21日17:00，调度器将其当成另一工作日再次发送。现场 NTP 未启用；谁或什么修改了系统时间尚未确定。本补丁不修改服务器系统时间、NTP或全局网络设置。

## 发送前检查

- `data/send-journal.json` 为独立持久发送登记，按应用/群绑定及北京时间日期保存发送意图、成功结果和消息标识。它不包含晨会正文、人员信息或密钥，不参与当天数据清理和诊断日志轮转。`send-journal.required` 防止日志丢失后被误当成首次安装。
- 第一次升级读取现有 `data/logs/service.jsonl*` 的成功发送记录；当前确认成功的卡片状态补齐消息标识。历史时间跳变、重复成功记录、日志损坏均暂停新发卡，不靠删除状态重新发。
- 先持久登记意图，再调用创建/发送；成功后登记确认结果。已有成功记录而当天状态丢失、同日消息标识不一致、结果未知、未完成的日志写入均禁止新发卡。崩溃后仍需核对原意图，不重置发送记录。
- 每15秒调度时比较系统时间与单调时钟，偏差超过2分钟暂停；每分钟持久保存时间检查点。重启后时间倒退超过2分钟或距检查点超过36小时也暂停，长时间停机需维护者核对。持续运行的正常周末、跨天不受影响。
- 日期异常时同时暂停历史清理和按异常日期归档，避免删除真实当天记录。已有确认卡片可在原有有效期及权限规则下继续处理提交；异常不解除已有未知提交保护。
- `status.sh` 的 `sendingBlocked` 和脱敏 `SEND_GUARD_BLOCKED` 事件记录原因。连接/已有群 `ready` 不等于允许发新卡。

## 维护处理

本次时间异常要先由公司技术核对并校准系统时钟。日志暂停标记不会因重启或时间改回来自动解除。

停止服务后，维护者应核对可信北京时间、两群当天原消息、当天状态、发送登记及归档；保留原始证据，分类处理异常未来日期的登记和状态。只有核对完成后才可调整检查点并解除 `blocked`。不要删除整个发送日志或 `send-journal.required` 来恢复；不要把已经发送或结果未知的登记改成未发送。当前日期仍与日志冲突时应继续暂停。

迁移、备份、恢复必须同时保留发送登记、标记文件与原卡状态。临时补班/手工发卡必须走带该登记校验的调度入口；旧临时脚本直接调用 `MeetingService.prepare()` 会绕开调度保护，禁止继续使用。不要为了验收向正式群发测试卡。

## 验证边界

局部检查覆盖日期前跳/后跳、正常跨天/周末、长时间停机、日志损坏/丢失/部分写入、同日重复/未知发送、状态日期及消息不一致、两群正常发送与重启防重、冻结时保留旧数据和已有卡片恢复。使用合成数据，无网络消息发送。生产部署及实际拦截结果以 Handoff 最新条目为准。
