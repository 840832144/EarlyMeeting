## 3. 当前范围：先跑通回调

本轮需要的 Capability 是：本机运行检查、可定位且脱敏的长连接诊断、现有卡片交互接收及表单字段核对。优先审查本机已有文件、已成功的发送工程、旧诊断工具与飞书官方 SDK。不要先升级或重装所有依赖，也不要增加通用机器人框架。

### 第一步：现场接管和复现

做什么：确认 Codex 当前 Host 是否就是 User 的 Windows 电脑；读取最新 Git 交接，核对本地仓库与未提交修改，找到 User 实际运行的测试目录。只检查获准项目相关进程，不清理或终止其他项目。先输出脱敏的版本/路径状态，再复现一次连接故障。

成功表现：能够区分实际入口请求、凭据校验、WebSocket 握手及回调配置等失败阶段，返回可支持判断的 HTTP 状态或安全错误码；记录根因与尚不确定项，不只重复 UNCLASSIFIED。

失败怎么办：当前会话不是目标电脑或缺少本机文件时，明确阻塞项并只请求必要的本机路径/启动动作；不能把云端或其他设备上的成功当成用户电脑修复。不要让 User 反复猜配置、关闭防火墙或提交完整日志。

### 第二步：最小修复和连接验收

做什么：根据复现证据作最小修改，使用已核对的官方 SDK 方式；本机持续运行一份测试接收程序。修改须有回滚办法。凭据由 User 在本机安全输入或通过已批准的受控环境读取，不回显。

成功表现：真实连接成功，有明确的连接状态证据；保持运行期间可进入应用后台完成卡片回调配置。启动提示、依赖安装成功或仅入口请求成功均不能代替握手成功。

失败怎么办：停止在已识别的故障阶段，给出明确原因与唯一下一动作；没有证据时不得降级证书校验、全局改代理或盲目重装运行时。涉及系统策略、应用权限或版本发布时，由 User 确认执行。

### 第三步：现有卡片真实提交

做什么：在已批准的测试群，用虚构文字提交现有卡片；核对 card.action.trigger 的接收和实际表单结构。需要模板信息时优先读取本机已有脱敏导出；确实缺失再请 User 提供去除内部标识与真实内容的模板 JSON，不猜字段。

成功表现：收到真实交互，表单字段确实存在且与测试输入相符。对外只保留固定状态、字段数量等必要脱敏证据，不打印原始回调。测试提示明确说明「本次仅验证回调，未保存、未更新」。

失败怎么办：区分没有连接、未配置回调、按钮未触发、表单未传值和群校验不通过；只修失败环节。收到按钮而无表单内容时，不标记填写通过。

### 第四步：交付本轮结果

做什么：提交最小修复、离线回归和目标本机实测摘要，提供一键启动、检查、停止与回滚说明。每一步说明做什么、成功表现、失败怎么办。Codex 能在本机完成的工作不再改成多轮由 User 下载替换压缩包。

成功表现：User 可按说明重复启动、完成一条测试提交并停止；连接和回调两项各自有证据。仅离线通过时仍标记待实测。

失败怎么办：STATUS 和 Handoff 保留真实未通过状态、失败阶段及下一动作，不报告机器人完成或已上线。

## 4. 验收与边界

本轮通过标准：确认实际运行环境；查清或可靠界定连接失败原因；目标本机连接成功；收到现有测试卡片的交互及表单数据；一键停止后不继续接收；诊断、测试与提交无凭据和原始敏感内容泄露。

本轮不做：保存真实晨会记录、更新公共消息、生产定时、管理后台、AI 总结、催填、周报、绩效、购买服务器、公网托管、开机启动或系统服务。没有群写入授权时不得发新的测试消息；优先使用现有卡片及明确告知的测试反馈。
