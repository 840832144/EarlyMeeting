## 2. 群里看到什么

按用户示意保留日期、分组、未到早会和今日交付。以下只展示占位成员，不能从截图推断真实名单或身份。

```text
某月某日晨会记录

【程序】
@成员A：待填写
@成员B：待填写

【策划】
@成员C：待填写
@成员D：待填写

未到早会：—

【今日交付】
—

[填写 / 修改我的内容]
```

员工只填写“今天做什么”，今日交付选填。提交后显示到自己的姓名后，再次提交修改自己的原条目。今日交付按成员顺序汇总并保留归属。

“未到早会”建议仅由配置的负责人维护；没有填写计划不能自动推断为缺席。负责人和成员分组在受控配置中维护，不做管理后台。编辑默认限于当天，昨天消息保留只读。

## 3. 首版只做这些

| 项目 | 规则 |
| --- | --- |
| 群范围 | 先支持一个明确配置的测试群；仅被拉进群不自动获得发送授权 |
| 定时 | 配置为工作日 10:00，时区显式设置；测试期定时默认关闭 |
| 测试入口 | 提供维护者可用的“立即发送测试卡片”入口，不必等到第二天 10:00 |
| 填写 | 在飞书内填写，自动识别本人，不手填或选择他人姓名 |
| 修改 | 更新自己的原条目，其他人的内容保留 |
| 汇总 | 始终更新当天的同一条公共消息，不另外发送汇总消息 |
| 历史 | 每个新工作日一条新记录，前一天不被覆盖 |
| 停用 | 一键关闭定时、一键停止服务，保留历史记录 |

不做多维表格、独立网页表格、管理后台、AI 总结、催填、周报、工时、绩效或完整任务管理。不要把晨会业务加入 Document Assistant，也不要依赖员工开着 Codex。

## 4. 开发方案与关键约束

### 4.1 先复用，再补业务

需要的 Capability 是：定时群消息、可信身份的卡片填写、共享消息原位更新、最小持久化。优先采用飞书企业自建应用的机器人能力、官方卡片组件与官方 SDK；本仓库只补晨会规则和部署入口，不重写 SDK，也不引入通用机器人平台或大模型框架。

建议采用一个轻量常驻服务和本地持久化存储，例如 SQLite；由 Codex 在现有 Host 上核对可用运行时后确定语言、SDK 版本和存储实现。优先验证官方长连接是否覆盖所需卡片回调；未经 User 授权，不开公网入口、不购买服务、不改其他项目的应用权限。

### 4.2 个人输入不得影响公共消息

公共卡片是全员已提交内容的共同视图。不得把公共卡片整体改成某位员工的个人编辑界面。个人填写容器应先按官方现行能力做最小验证，不能未经验证就承诺任意弹窗。

必须验证：甲正在输入时，乙提交引发公共卡片刷新，不得清空甲的未提交内容，不得导致甲覆盖乙。若现有卡片输入方式不能满足，应先报告具体限制和最小调整方案；不得擅自改为外部表格、每人一条公共消息或强制私聊流程。

### 4.3 数据保存与原位更新

按“群 + 业务日期”保存当天唯一消息标识；按“当天记录 + 经验证的操作人身份”保存个人条目。身份来自经官方 SDK 验证的交互上下文，不能信任表单传入的姓名或成员标识。负责人操作同样需要校验。

个人数据先持久化，再从最新完整数据合并并串行刷新原消息。同一消息的旧刷新不能晚于新刷新覆盖结果；合并连续刷新并对失败退避。重复事件只处理一次；同一人打开旧内容再提交时，检测版本冲突并提示重新加载。

保存失败不能显示成功。已保存但卡片更新失败时，应明确提示“已保存，群记录待刷新”，只重试原消息，不能补发新卡片。输入需要安全转义，长度与整卡大小在发送前检查，不能因一条过长内容导致全员卡片失效。

### 4.4 发送、重启和测试去重

发送前持久化发送状态和稳定去重标识，结合官方发送接口当期能力处理超时与不确定结果。不能因未收到返回就判定未发送并盲目重发。服务重启恢复当天的消息关联，不能再发第二份模板。

手动测试入口与定时发送共用“群 + 业务日期”的去重规则；重复点击测试默认复用当天消息。测试群中的多轮测试不得自动删除已有员工数据。错过发送时间或停机后重启，不自动补发历史日期；由维护者确认当天是否需要手动发送。

配置的定时开关和测试群白名单在默认安装状态均不启用外部发送。不得自动发现并向所有加入的群广播。

### 4.5 安全与运行

本仓库当前为公开仓库。App Secret、token、真实成员标识、群标识、员工计划、运行数据库、原始回调、完整响应与敏感日志不得提交 Git 或贴到聊天。示例配置仅使用占位符，实际值由 User 在获准的本机环境配置；开发交付需包含正确的忽略规则。

只申请完成目标所需权限，不采集整个群的聊天历史。凭据缺失、身份不符、群未批准或权限不足时停止对应写入并提供脱敏错误。测试使用虚构工作内容，截图和证据脱敏。

正式定时运行需要持续在线的服务；员工不需要开着 Codex。常驻设备、应用配置、权限、测试人员可用范围和任何外部发布由 User 确认。首次安装不得自动变更开机启动、系统服务或生产调度。

## 5. 开发与测试顺序

### 阶段一：完成实现准备和离线开发

先完成正式任务登记与冲突检查，再在 EarlyMeeting 独立分支实施。先做卡片结构与交互模型的最小验证，再补身份校验、持久化、定时和去重。离线测试使用模拟接口与占位成员，不向真实群发送消息。

成功表现：有可运行程序、测试结果和一键安装、启动、检查、停止、手动测试入口；文档逐步说明操作，不要求用户读代码。没有真实飞书联调证据时，状态只能写“可进入测试群联调”，不能写“已上线”或“卡片验收通过”。

失败怎么办：停在失败步骤，返回脱敏原因和唯一下一动作；不能用扩大权限或改动其他业务仓库绕过。

### 阶段二：User 创建测试群并拉入机器人

机器人在飞书中的应用配置、授权和受控服务启动准备好后，由 User 建一个内部测试群，将机器人加入。测试只使用该批准群；名单先配置少量测试成员。

成功表现：机器人可加入目标群，检查入口确认身份、卡片回调和发送权限准备好，定时仍关闭。

失败怎么办：按问题分别核对应用配置、可用范围、群限制或服务连接；不要反复创建应用，不索取或回显 Secret。

### 阶段三：立即发卡片，验证同一条消息

由维护者执行“立即发送测试卡片”，无需等待 10:00。User 和另一位测试成员分别填写，再同时填写，然后修改本人条目；同时在手机和桌面端检查。

成功表现：所有已提交内容都在原卡片中，消息标识不变，没有额外公共晨会消息；其他人刷新不会破坏正在填写的内容。

失败怎么办：保持定时关闭，保留原消息和已提交数据，修复后对同一问题重验。只有一个测试成员时，并发和跨用户测试保持待验收，不能由开发者勾选通过。

### 阶段四：确认后开启 10:00 定时

卡片联调通过后，由 User 确认启用目标群的工作日 10:00 定时。切换到正式群另行明确批准，不沿用测试授权。

成功表现：在实际工作日 10:00 发出唯一模板，普通休息日不发，人工配置的例外日期按规则执行；停止服务或关闭定时后不再自动发送。

失败怎么办：先关闭调度，不重复补发；核对服务在线状态、时区、日期规则和发送记录，再按原消息恢复。
