卡片现在有 **策划、程序、今日交付** 三个同级区域。前两区各人填写自己的记录；今日交付是全群共同维护的一个文本框。

## 日常操作

1. 双击 **START_MEETING.cmd**，保持电脑开机、联网，程序持续运行。沿用本机凭据 JSON，不用重新输入密钥。
2. 在当天卡片的 **策划** 或 **程序** 区域点 **＋ 添加我的一行**。分区标题为 24px 加粗，姓名自动带入；新行右侧显示红色 **未提交**，填好后点击这个按钮即可提交。成功后变为蓝色 **提交**，后续修改仍点击它。
3. 选错区域时，点本人行的 **删除**；行消失后到正确区域重新添加。删除会移除该行已保存内容，新行从空内容开始。三个群均仅本人可保存和删除；每人每卡最多一行。
4. **CHECK_MEETING.cmd** 查看状态，**STOP_MEETING.cmd** 停止。重启恢复当天同一卡片与已保存记录，不重复发消息。

每行按人员、晨会内容、操作排列，右侧短按钮“提交 / 删除”并排；内容列宽 340px，操作区 92px，内容框默认一行，达到列宽后自动换行并增高，记录间距为 4px。每张卡片最多 20 行、每行最多 300 字，同时受整卡容量限制。输入时不保存；点击后“已排队”表示已接收，请等本行刷新才算保存完成。其他人无法保存或删除你的个人行。

多人同时提交不同的行会在本群依次保存，不影响其他群。同一行排队或保存时再次点击，会提示等待本行刷新；不会重复执行。今日交付是同一份共享内容，同一时刻只接受一个更新，其他人需等它刷新后再编辑提交。

红色“未提交”针对从未成功提交过的新行（revision=0），包含按名单预建的行；仅输入文字不会解除提醒，只有 API 更新与本机保存成功后才转为蓝色“提交”。已提交行的客户端草稿修改尚未上传，程序无法据此实时改色；本次不新增输入监听。

按查看者隐藏他人按钮的需求已记录，但当前 JSON 2.0 共享卡片模式不提供逐查看者按钮布局。没有将隐藏需求冒充为已实现；继续由服务端按群配置校验操作权限，不为此改为独享卡片或增加其他页面。依据：[卡片 JSON 2.0 结构](https://open.feishu.cn/document/uAjLw4CM/ukzMukzMukzM/feishu-cards/card-json-v2-structure)。

## 今日交付

本区直接显示“交付内容 / 操作”两列，不用添加行，不显示人员列。所有群成员均可修改共享文本，点“未提交 / 提交”保存；点“删除”清空内容，输入框与区域保留。空内容显示红色“未提交”，提交成功后显示蓝色“提交”。默认一行、内容达列宽自动换行，最多 300 字。

这是全群共享的一份当天交付内容。修改或清空都同步到同一条卡片；重启保留，每个群与日期独立。若别人先提交，旧版本操作会被拒绝，请在最新内容上修改。策划/程序行另按各群 row_permissions 控制；今日交付本身不依赖读取群成员或增加应用权限。

## 遇到提示时

- **ALREADY_RUNNING**：使用现有进程，同一应用只运行一份；诊断与晨会模式互斥。
- **已经在某区有一行**：继续填写已有行，或删除本人行后换区添加。
- **只能保存或删除自己创建的那一行**：操作本人姓名的行。
- **该行已更新**：使用最新卡片上的按钮。
- **已排队**：等待本行刷新，不要反复点击。第一次提交成功时红色“未提交”变为蓝色“提交”。
- **这一行已有操作排队或正在保存**：该行尚未刷新，保留输入并等待；其他行仍可提交。
- **UPDATE_UNCONFIRMED / QUEUE_PAUSED / MEETING_NOT_READY**：结果尚未确认，本群队列保留；交维护者恢复，不删文件强行重发。其他群独立处理。
- **MESSAGE_SEND_UNCONFIRMED**：50 分钟内重启只重试同一请求；超时先核对群消息。
- **LOCAL_STATE_INVALID**：核对本机群配置和状态文件，不上传凭据或原始文件。

## 维护者说明

一个官方 SDK 长连接服务所有配置群，回调核对实际群、当天消息、操作者、行归属与版本。布局 v9 每行一个水平根表单，姓名宽 80px、内容宽 340px、右侧为提交/删除，与表头列宽一致；输入超过本列宽度自动换行并向下增高，姓名和按钮保持顶部对齐，不再设置六行高度上限。窄窗口可能由飞书自动换行。服务端只保存实际操作者该行字段，不保存或输出原始回调。客户端不设置必填以便删除空行；保存仍由服务端校验本人内容非空及长度。使用原生水平排列减少容器数量，保留整卡 200 元素与 20 行预算。

新增用 `cardElement.create(insert_before)`，保存用 `cardElement.update`，删除用 `cardElement.delete`。布局迁移直接更新最近一条原消息并保留已保存行；本次按 User 最新要求取消补发，不创建新消息。后续操作只改对应行。

当前布局 v11 在原个人行后添加 delivery_form，共享 delivery.content / revision 存在同一份按群/日期状态中。共享提交/清空仅更新此表单，使用独立内容版本与全卡递增序号；清空也递增版本，避免旧操作复活已清空内容。原个人行仍检查 owner。共享内容不占个人行名额，沿用整卡容量限制、操作去重与待确认意图。状态日志仅新增 DELIVERY_SAVED / DELIVERY_CLEARED 等固定代码，不含输入文本。

`.local/meeting/` 仅当前 Windows 用户与 SYSTEM 可访问。状态按 `days/<应用与群的哈希>/<北京时间日期>/meeting-state.json` 独立保存。首次升级复制并核对原状态，保留原卡片、消息和两行记录；原文件作为历史备份，不再作为运行状态。不要删除该目录来“重新发送”。

发送 UUID、更新 UUID、递增序号和意图先原子保存再请求飞书。结果不明确或 UUID 冲突保持待确认，不冒充成功。各群单独处理失败；定时失败不盲目另建卡片，核对后重启从同一状态恢复。输出仅状态码与数量，不保留原始回调、完整 SDK 日志、回调 token 或通讯录。

并发处理采用每群/当天独立的 `requests` 队列，最多24项，先原子保存经过校验的提交字段，再回应“已排队”。同一目标只保留一个在途操作；入队时计算排队请求合计的行数及整卡容量。更新成功后重新读取最新状态，在一次原子保存中提交该行并移除对应请求，保留异步等待中新排入的其他请求。旧状态没有 `requests` 时视为空队列，已保存行无需迁移。

网络结果未知时停止本群队列，保留原更新 UUID/sequence 和全部后续请求。维护者双击 **STOP_MEETING.cmd**，确认停止后再双击 **START_MEETING.cmd**；当天恢复会先重试原意图，明确成功后才处理后续队列。若仍显示待确认，保留数据交维护者处理，不清空 pending、队列或状态文件。代码升级前备份在 `.local/meeting/code-backup-before-concurrency/`；有未完成队列时不可直接回退到不识别该队列的旧代码。
